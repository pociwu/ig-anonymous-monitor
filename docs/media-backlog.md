## 只下載既有 IGWatcher 佇列

在正式部署目錄執行（先使用已包含本功能的映像）：

```bash
cd /srv/ig-monitor
docker compose run --rm --no-deps monitor python -m ig_monitor --config /srv/ig-monitor/config.yaml --download-pending
```

此模式與一般巡檢共用 `monitor.lock`，不重新查個人頁、Stories 或粉絲名單。
每次逐筆處理，每筆間隔 10 秒，每帳號最多 `schedule.media_limit_per_account` 筆；
只處理啟用且最後保存的快照為公開的帳號。IGWatcher 個人頁或分類擷取失敗
不再連帶阻擋既有媒體佇列；不會因此清除帳號失敗紀錄或宣告帳號恢復。
私人、公開狀態未知、停用帳號及來源全域冷卻仍會阻止下載。
沿用既有下載驗證、去重、Telegram 附件選項與來源守門機制。
舊來源資料不混入 IGWatcher 下載，不會清除或偽造完成狀態。

來源全域冷卻時不送出下載請求；遇驗證、拒絕存取等阻擋立即停止整批。
媒體下載成功不代表來源 API 已恢復，因此不解除來源冷卻或登入帳號風控。
到期僅代表允許下次嘗試，不保證可下載；此命令不建立額外排程。
一般巡檢仍維持原有擷取順序，逐筆退避也適用於一般巡檢的下載佇列。
# 查詢與下載冷卻拆分（2026-09-28）

IGWatcher 的查詢冷卻沿用 `igwatcher` 狀態；下載拒絕使用 `igwatcher:media` 獨立狀態。
只有診斷明確為 `http_status=403 phase=api signal=http_status` 的查詢拒絕不影響下載；不刪除舊冷卻紀錄。429、明確 challenge、下載端拒絕及範圍不明的舊來源錯誤仍阻擋下載。下載端 429/challenge 也記錄查詢暫停。

排程查詢冷卻時仍會執行下載佇列；正常巡檢結束後以新的下載工作階段執行，避免沿用查詢端的本輪 blocked 狀態。兩者仍共用 monitor.lock，不平行搶同一筆。下載逐筆執行、間隔 10 秒，沿用每帳號上限、媒體去重及逐檔退避；不以增加並行量放大來源負荷。
# 貼文下載連結刷新（2026-09-28）

`igwatcher_media_transport: browser_proxy` 的正式 Posts 佇列下載現在先刷新來源連結：使用正常網頁查詢帳號和第一頁貼文，依原父貼文 ID 找到目標；若為 `anon:true` 摘要，點開該卡片取得完整貼文，再要求 shortcode／父 ID 相符。只能以同一父貼文內唯一且非通用的完整媒體檔名對應舊連結，不能按輪播位置猜測。

刷新後網址僅用於本次傳輸，不覆寫歷史 URL／輪播觀測或提高作者歸屬；下載後沿用既有 MIME、內容、去重、存檔及通知流程。同一父貼文在本輪成功刷新後暫存最多 180 秒，避免每張輪播重查；失敗不重試、不回用舊網址。

刷新必須同時通過查詢和下載冷卻。刷新端拒絕記入查詢冷卻；純冷卻略過不新增冷卻次數。網頁資源限制同源 GET，禁止自動載入媒體預覽、其他分類和第二頁，每次最多 40 個請求、90 秒。401/403/422/429 或驗證訊號停止。

範圍限制：目前僅 Posts 第一頁可定位的原貼文／輪播；Reels、Stories、Highlights 尚未加入此刷新器。原貼文不在第一頁、檔名改變或沒有唯一關聯時，保留並逐筆退避，不能保證全部積壓都能復原。

驗證：本地正式佇列介面測試，以及 OCI `--network none` Chromium 的完整資料／延遲輪播／403／錯誤身分案例。OCI `142027` 隔離真實驗證由新模組自行刷新並下載 87,658 bytes、1440×1440 WebP，SHA-256 與先前驗證相同；未在隔離測試中改寫正式佇列。
